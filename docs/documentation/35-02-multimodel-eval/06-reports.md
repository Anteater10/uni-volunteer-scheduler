# 35-02-F — Reports: CSV + traces JSON + auto-rendered markdown

> Documentation companion to sub-phase 35-02-F. Covers the three output
> artifacts the eval harness produces and the contracts each one holds.

## Why this sub-phase exists

The eval harness produces raw per-question traces; that data has to be
funnelled into three different consumers:

1. **The paper.** Andy's paper LaTeX `\input{}`s a CSV directly. Any drift
   in column order silently breaks the table.
2. **The reviewer / future-Andy.** A human-readable markdown report he can
   skim and a JSON bundle he can grep when something looks wrong.
3. **The top-level index.** A single short page (`docs/documentation/35-eval-results.md`)
   that the rest of the project can link to without knowing the path
   inside `35-02-multimodel-eval/`.

Each consumer has a different drift tolerance, which is why we ship three
artifacts instead of one.

## Artifact 1 — `results.csv` (paper-facing, schema-locked)

Path: `backend/eval-results/{timestamp}/results.csv`.

Columns (locked — regression-guarded by `test_csv_header_is_locked`):

```
model, question_id, category, role,
ragas_faithfulness, ragas_answer_relevancy, ragas_context_precision,
tool_use_correct, outcome,
latency_ms, prompt_tokens, completion_tokens
```

Twelve columns; same order forever. The locked-header test asserts byte
equality with the spec ordering so any accidental rename or reorder
fails CI before it can poison a paper table.

Empty values follow two conventions:

- `None` numeric values serialise as the empty string (CSV-idiomatic;
  RAGAS often returns `None` for `context_precision` when the question
  is not retrieval-based).
- `tool_use_correct` is `"true"` / `"false"` when the question is
  agentic and the empty string when it is non-agentic — we deliberately
  do NOT mix this column with `0` / `1` because the paper distinguishes
  "non-agentic" from "agentic-and-failed".

This matches the Phase 32 `rerank-lift.csv` precedent (`metric,
rerank_off, rerank_on, lift`) — same locked-header discipline.

## Artifact 2 — `per-question-traces.json` (debug / grep bundle)

Path: `backend/eval-results/{timestamp}/per-question-traces.json`.

Plain JSON array of trace objects. No schema lock — fields are
additive over time as new metrics surface. The writer (`write_traces_json`)
uses `default=str` so dataclasses and `datetime` objects serialise without
the caller having to flatten them first.

Use this artifact when:

- A CSV row looks wrong and you need the full prompt / tool calls /
  retrieved chunks to diagnose.
- You want to write a one-off Jupyter cell that pulls a custom slice.
- You are comparing two runs and need diff-friendly raw data.

## Artifact 3 — `results.md` (auto-rendered, sub-phase-local)

Path: `docs/documentation/35-02-multimodel-eval/results.md`.

Auto-generated by `render_markdown`. Five sections, fixed order:

1. **Headline** — one row per model. Mean RAGAS scores, tool-use %,
   thumbs-up rate from Phase 35-01, total rating count (with `*` marker
   when below the 10-rating insufficient-sample threshold).
2. **Per-Category Breakdown** — one sub-table per question category
   (`refusal`, `tool_use`, `profile_recall`, etc). Shows whether one
   model dominates a single category or whether ranking is uniform.
3. **Adversarial Pass Rates** — ASCII bar charts (Unicode block
   characters) per model × per adversarial category, fenced in a code
   block so they render correctly in plain-text viewers.
4. **Failure Taxonomy** — bullet list of every adversarial fail with a
   pointer to the per-question trace file. This is what drives paper
   contribution #3.
5. **Sample Size & Caveats** — counts of `empty_response` and
   `transient_failure` outcomes per model, plus the insufficient-sample
   asterisk legend.

The hand-edit hazard is the same as any auto-rendered artifact: if Andy
hand-edits this file and then re-runs the harness, the next render
overwrites his edits. The "do not hand-edit" banner at the top of the
rendered file is the warning.

## Artifact 4 — `docs/documentation/35-eval-results.md` (top-level redirect)

Hand-written index page. Lives at the top of `docs/documentation/`
so the paper, README, and `STATE.md` can link to a stable path that
does not depend on the sub-phase directory name.

The companion renderer `render_top_level_redirect` is currently a
`NotImplementedError` stub — the page is hand-written until after the
first real multi-model run produces a fillable headline ranking. Once
the renderer ships in a follow-up, re-runs regenerate this file too.

## Why three formats instead of one HTML dashboard

We deliberately do not ship an HTML dashboard for this phase:

- A static markdown report is greppable and diffable in git.
- A CSV is the lowest-common-denominator input for the paper, for
  pandas, and for a future Jupyter notebook.
- A JSON bundle covers the "I want everything raw" case.

An HTML dashboard would add a build step, a JS dependency, and a hosting
question — none of which earn their keep until we have more than one
real run to compare.

## CI coverage gate

A new gate at `app.eval = 90 %` lands with this sub-phase (current
branch-coverage reality is 90.53 %, which displays as 91 % in the
rounded summary row), with a TODO to raise it to 95 % once the deferred
wiring lands. The gate measures `app.eval` only — the sub-package
`app.eval.metrics` is folded in because `--cov=app.eval` recurses.

The gap between 90 % and the project-wide 95 % convention
(`app.copilot`, `app.copilot.retrieval`, `app.copilot.feedback`,
`app.corpus`) traces to three deferred production-wiring TODOs:
`adversarial._run_one_case` (71 %), `run.py` (82 %), and `replay.py`
(89 %). Those branches need a real model call or a real replay fixture
to exercise, not a unit test mock, so they ship together with the
35-02-G wiring work. Landing the gate at 91 % locks in current reality
and prevents regression — the actual purpose of a coverage gate — without
breaking CI on day one. Once 35-02-G ships, the gate bumps to 95 % and
the TODO comment in `ci.yml` comes out.

## Reproducing a report locally

```bash
python -m app.eval.run --models all --testset default
```

Outputs land in `backend/eval-results/{timestamp}/` and
`docs/documentation/35-02-multimodel-eval/results.md`.
