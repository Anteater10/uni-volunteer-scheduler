**Step 0 is decided: SendGrid.** UCSB uses SSO federation and does not issue IAM
user credentials, and SES SMTP credentials are derived from an IAM user's access

## NEW finding — found today, on the SendGrid path, HIGH

**F6 — a missing SendGrid env var silently sends nothing, and reports success.**

`app/celery_app.py:144`

```python
if not settings.sendgrid_api_key or not settings.email_from_address:
    logger.warning("sendgrid_api_key or email_from_address missing; skipping send to=%s", ...)
    return          # <-- returns normally
```

`_send_email` sees no exception. The Celery task succeeds. The caller believes
the mail went out. Nothing surfaces except one warning line in a log nobody is
tailing.

**Why this is worse than it looks.** This is an account-less product: email *is*
the app. Magic links, signup confirmations, reminders and promotions are the only
channel a volunteer has. A typo'd `SENDGRID_API_KEY` on the AWS side means every
volunteer silently receives nothing while the app reports every send as fine —
and the failure mode is indistinguishable from "nobody signed up this week."

**It is the same bug the docstring 40 lines below claims was fixed.** That
docstring says *"previous silent-swallow behaviour masked misconfigured sender
identities for weeks."* The swallow was fixed in `_send_email`'s exception
handler; the **missing-config branch one layer up still returns silently.** Same
class, same consequence, still live.

**Fix:** assert at startup, not per-send. `email_mode == "sendgrid"` with either
value absent should refuse to boot, exactly as `EXPOSE_TOKENS_FOR_TESTING` +
`ENVIRONMENT=production` already does in `config.py`. Fail closed at boot beats
failing silent per message. ~1 hour including a test.

**Related, smaller:** `config.py:53` comments `email_mode="smtp"` as *"prod: AWS
SES SMTP"*. Now wrong — correct it while you are in there so it does not teach
the next person the thing we just ruled out.
